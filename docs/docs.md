# 1. 프로젝트 비전과 성공 지표

## 프로젝트 목표

탄소 중립 대전 지역특화 프로젝트

## 프로젝트 목적

3인으로 구성된 팀프로젝트로, 대전이라는 지역에 특화된 탄소 중립 주제의 앱 개발 프로젝트를 진행합니다.

## 이 프로젝트를 지금 시작해야 하는 이유

- 2025년부터 활발하게 이루어진 대전시의 탄소 중립 관련 정책 → 지금 시작해야 공공 지원 가능성이 높음

## 핵심 가치

1. 대전 시민들의 더 많은 탄소중립 관련 지식 함양
2. 대전에서 진행 중인 탄소중립 관련 사업의 참여율 증가

## 핵심 기술

- 타슈 이용 지도
- 타슈 이용 경로 추적 기능
- 탄소 절감량 계산 기능
- 타슈 이용 리포트 제도, 리포트 목록 조회 기능
- 포인트 제도 (포인트는 적립되게만 구현, 사용처는 추후 결정)

## 부가 기술

- KPI 수치 측정을 위한 지식 퀴즈 기능
- 사용량 측정 모듈
    - └ 목적: 추후 실제 운영 플랫폼에서의 데이터 수집 경험 축적
- QR 큐싱 감지기
- 지역구 탄소절감 경쟁 리더보드 (팀장 제안, 시간 여유 시 구현)
    - └ 앱 초기 설정 시 거주 중인 대전 5개 지역구 / 관광객 선택

## 미래 후보 기능

- 국가 시행 탄소중립포인트 제도 연동
- 적립된 포인트 사용처 확립 (제휴, 광고 가맹)
- 탄소 최저 절감 경로 추천 기능 (로직 고도화 후 구현 검토)

# 6. 아키텍처 및 데이터 구조

## 6-1. 전체 아키텍처 구조

서버는 단일 서버로 운영하되, 내부를 역할별로 분리하는 구조를 채택합니다.

### 구조 다이어그램

```
[React Native 앱 (Expo)]
        ↕ HTTPS
[서버 (Node.js + Express)]
  /proxy  ← 인증, API 키 보호, 요청 중계
  /core   ← 탄소계산, 포인트, 리포트, 퀴즈, KPI
  /db     ← Firebase 연동
        ↕                         ↕
[Firebase]               [외부 API 서버]
  ├─ Firestore (DB)        ├─ 카카오맵 API
  └─ Auth                  └─ 공공데이터포털 (타슈 대여소)

[기기 내부]
  └─ expo-location (GPS 센서 직접 읽기, 네트워크 없음)
```

## 6-2. 클라이언트 구조

### 화면 (Screens)

- `AuthScreen` — 로그인 / 회원가입
- `OnboardingScreen` — 대전 5개 지역구 / 관광객 초기 설정
- `MapScreen` — 지도 + 이용시작/종료 + GPS 경로 표시
- `ReportScreen` — 이용 후 1회 리포트 출력
- `ReportListScreen` — 리포트 목록 조회
- `MyPageScreen` — 마이페이지 + 포인트 잔액 + 적립 로그
- `QuizScreen` — 지식 퀴즈 (초기 / 재측정)
- `PermissionScreen` — 권한 허용 현황 확인

### 모듈 (Modules)

- `rideModule.js` — 이용시작/종료 트리거, GPS 추적 (watchPositionAsync)
- `carbonModule.js` — 탄소 절감량 계산 (로직 A: 고정 배출계수)
- `pointModule.js` — 포인트 적립 계산
- `qrModule.js` — QR 스캔 + 큐싱 감지 (도메인 검증)
- `usageModule.js` — 사용량 측정 + KPI 로그 전송

## 6-3. 서버 API 엔드포인트

### /auth

- `POST /register` — 회원가입 (유저 정보 암호화 처리)
- `POST /login` — 로그인

### /ride

- `POST /start` — 이용시작 기록
- `POST /end` — 이용종료 + 리포트 자동 생성

### /report

- `GET /list` — 리포트 목록 조회
- `GET /:id` — 리포트 상세

### /point

- `GET /balance` — 포인트 잔액
- `GET /log` — 포인트 적립 로그

### /map

- `GET /stations` — 타슈 대여소 위치 (공공데이터포털 프록시)

### /quiz

- `GET /questions` — 퀴즈 문제 조회
- `POST /submit` — 퀴즈 제출 + KPI 기록

### /usage

- `POST /log` — 사용량 측정 데이터 수집

## 6-4. DB 구조 (Firebase Firestore)

### 저장 데이터

```
users/{userId}
  ├─ profile       — 이름, 이메일
  ├─ region        — 대전 5개 지역구 / 관광객 여부
  └─ pointBalance  — 포인트 잔액

rides/{rideId}
  ├─ userId
  ├─ startTime / endTime
  ├─ coordinates[] — GPS 경로 좌표 배열
  ├─ distanceKm
  └─ carbonReductionKg

reports/{reportId}
  ├─ rideId        — 라이드 참조
  ├─ distanceKm
  ├─ durationMin
  ├─ carbonReductionKg
  └─ pointsEarned

pointLogs/{logId}
  ├─ userId
  ├─ amount
  └─ earnedAt

quizResults/{resultId}
  ├─ userId
  ├─ score
  ├─ takenAt
  └─ type          — initial / retest (KPI 비교용)

usageLogs/{logId}
  ├─ userId
  ├─ action        — 사용한 기능
  └─ loggedAt
```

### 저장하지 않는 데이터

- 타슈 대여소 위치 — 공공데이터포털에서 실시간 호출
- 지도 렌더링 — 카카오맵 서버가 처리
- 퀴즈 문제 원본 — 서버 파일로 보관, DB 불필요
- GPS 원시 데이터 — 이용 중에만 사용, 종료 시 경로 좌표만 저장

# 7. 기술 스택 결정

각 기술 스택의 선택 이유와 확정 근거를 기록합니다.

## 7-1. 확정된 기술 스택

### 앱 — React Native (Expo)

- iOS / Android를 코드 하나로 동시에 개발 가능
- Expo가 GPS(expo-location), 카메라(QR 스캔) 등 필요한 네이티브 기능을 라이브러리로 제공
- 3인 팀이 2주 안에 개발하기에 적합한 러닝커브

### 서버 — Node.js + Express

- JavaScript 기반으로 React Native와 언어가 통일되어 팀원 모두 프론트/백을 넘나들며 협업 가능
- Express는 가볍고 설정이 단순하여 빠르게 서버 구축 가능
- 2주 일정에서 러닝커브가 낮은 것이 중요한 선택 기준

### DB + 인증 — Firebase (Firestore + Auth)

- Auth 내장으로 로그인/회원가입을 별도 구현 없이 빠르게 붙일 수 있음
- Firestore의 실시간 동기화가 GPS 경로 좌표처럼 자주 업데이트되는 데이터에 적합
- DB와 인증을 하나의 플랫폼에서 통합 관리 가능
- 무료 플랜(Spark)으로 팀프로젝트 규모 충분히 커버
- 검토한 대안: Supabase (PostgreSQL 기반, SQL 유연성 높으나 국내 레퍼런스 부족), MongoDB Atlas + JWT (커스터마이징 자유로우나 인증 직접 구현 필요로 2주 내 부담)

### 지도 — 카카오맵 API

- 무료 제공, 일 300,000회 쿼터로 팀프로젝트 규모에서 충분
- 국내 도로/골목 데이터 정밀도가 가장 높음
- 한국어 문서와 국내 커뮤니티 레퍼런스 풍부
- 검토한 대안 및 제외 이유:
    - 네이버 지도 API — 2025년 3월부터 신규 이용 신청 차단 및 무료 이용량 중단으로 제외
    - 구글 맵 API — React Native 공식 지원이 좋으나 유료 (카드 등록 필수), 국내 데이터 정밀도 낮음
    - 통계청 API — 지도 렌더링 불가, 지역별 통계 데이터 제공용으로 지도 API와 용도 불일치 (리더보드 보조 데이터 용도로는 활용 검토 가능)

### GPS — expo-location

- React Native + Expo 환경의 표준 라이브러리
- watchPositionAsync로 이용 중 실시간 경로 추적 가능
- 권한 요청 기능 내장으로 접근성 요구사항(권한 허용/비허용 요청)과 자연스럽게 연결
- 기기 GPS 센서를 직접 읽는 방식으로 별도 네트워크 요청 없음

### 외부 데이터 — 공공데이터포털

- 타슈 대여소 위치 데이터를 공식 제공하는 유일한 출처
- 대전시 공공자전거 API 등록되어 있어 별도 크롤링 없이 합법적으로 데이터 수집 가능

# 8. 브랜치 및 커밋 전략

## 8-1. 브랜치 전략

### 브랜치 구조

- `main` — 배포용 (기본 브랜치, 최종 완성본만 병합)
- `dev` — 개발용 통합 브랜치
    - `feature/{기능명}` — 기능별 개발 브랜치 (dev에서 분기)

### 병합 흐름

`feature/*` 개발 완료 → `dev`에 merge → 프로토타입 테스트 (1차, 2차) → 2차 테스트 완료 후 `main`에 merge

### 브랜치 네이밍 규칙

- 소문자 케밥케이스 사용
- 예시: `feature/map-screen`, `feature/carbon-module`, `feature/login`

## 8-2. 커밋 메시지 전략

### 포맷

- 첫 줄: 헤더 — 이번 커밋에서 변경된 사항을 한 줄로 요약하여 기재
- 본문: 이번 커밋에서 변경된 사항을 1, 2, 3, ...으로 구체적으로 기재

**예시**

```
feat: 탄소 절감량 계산 로직 구현

1. carbonModule.js 고정 배출계수 계산 함수 추가
2. 교통수단별 배출계수 상수 정의 (자가용/버스/지하철)
3. g → kg 변환 및 소수점 둘째 자리 처리
```

### 주요 전략 헤더

- `feat` — 새로운 기능 추가 | `feat: 탄소 절감량 계산 로직 구현`
- `fix` — 버그 수정 | `fix: 서버리스 함수 타임아웃 오류 수정`

### 보조 전략 헤더

- `docs` — 문서 수정 | `docs: API 명세서 업데이트`
- `refactor` — 코드 구조 개선 | `refactor: carbonModule 함수 분리`
- `chore` — 빌드 설정, 패키지 설치 | `chore: expo-location 패키지 추가`
- `test` — 테스트 코드 추가/수정 | `test: 데이터 변환 함수 단위 테스트 추가`
